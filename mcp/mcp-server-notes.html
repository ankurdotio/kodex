01
The Problem
Why does MCP even exist? Meet the Google Calendar situation.

Suppose you are building an AI chat application. You want your agent to work with Google Calendar — create events, check the schedule, all of it.

So you sit down and write tools for your agent: read the Google Calendar API docs, handle authentication, write a create_event tool, a list_events tool, test everything, fix the bugs. A few days of work.

Here is the thing — you are not alone. Hundreds of companies are building their own AI chat applications, and they all decide the same thing: "our agent should work with Google Calendar." So hundreds of teams write the exact same tools, against the exact same API, fixing the exact same bugs.

Company 1 → writes Google Calendar tools
Company 2 → writes the same tools again
Company 3 → writes the same tools again
... Company 500 → same tools, again
    ↓
Google changes the API
    ↓
500 codebases break. 500 teams fix the same bug. ❌

And Calendar is just one service. Your agent also wants Gmail, Slack, GitHub, Notion... every AI app × every service = a separate integration. This is called the M × N problem.

Key Concept — The M × N Problem

M AI applications wanting to talk to N services means M × N custom integrations. 100 apps × 10 services = 1000 copies of basically the same tool code, all maintained separately.

In the Google Calendar story, what exactly are hundreds of companies repeating?

10 AI apps each integrate 6 services directly. How many integrations must be built and maintained?

02
The Solution — MCP Server
Google flips the model: the tools move to Google's side.

Now Google looks at this mess and makes a decision: "we will build a server with tools." Not an AI. No model, no agent — just tools.

These are the same kind of tools we already write for our agents. The difference? They are not created on our server. They live on Google's own server, and they have direct access to Google's API.

What does this protect us from? Hundreds of companies no longer write the same tools again and again. Google writes the tools once, and everyone connects their agent to them.

Google writes the Calendar tools ONCE → MCP Server
    ↓
Your agent → connects
Claude / Cursor / ChatGPT → connect
Company 1 ... 500 → connect
    ↓
Google updates one server → everyone gets the fix ✅
Key Concept — MCP

MCP (Model Context Protocol) is an open standard that defines one unified structure for exposing tools to AI systems. An MCP server exposes the tools; an MCP client (inside your AI app) consumes them. Build tools once — use them with any AI system.

Think of it like USB-C. Before USB-C, every device needed its own charger. One standard port later — any charger works with any device. MCP is that port, but for connecting AI apps to services.

What Without MCP With MCP
Who writes the tools Every company, separately The service provider, once ✓
Where tools live Inside each app's codebase On the provider's MCP server ✓
API changes Break hundreds of codebases Fixed in one place, for everyone ✓
Integrations needed M × N M + N ✓
💡

MCP was created by Anthropic (the makers of Claude) in late 2024 as an open protocol. Today it's adopted across the industry — which is exactly why learning it once pays off everywhere.

Step 2 — Create the MCP Server + a Tool

This is the heart of everything. registerTool here is the MCP version of the tools we've been writing for our LangChain agents — same idea, unified structure.

mcp/mcp.server.ts 
import { McpServer } from "@modelcontextprotocol/server"
import * as z from "zod/v4"

export function getMcpServer() {

    const mcpServer = new McpServer({
        name: "weather",
        version: "1.0.0",
    })

    mcpServer.registerTool(
        "get_weather",
        {
            title: "Get Weather",
            description: "Get the current weather for a given city.",
            inputSchema: z.object({
                city: z.string().describe("The name of the city to get the weather for."),
            }),
            outputSchema: z.object({
                temperature: z.number().describe("The current temperature in Celsius."),
                description: z.string().describe("A brief description of the current weather."),
            }),
        },
        async ({ city }) => {
            return {
                content: [{
                    type: "text",
                    text: `The current weather in ${city} is 25°C and sunny.`,
                }],
                structuredContent: {
                    temperature: 25,
                    description: "sunny"
                }
            }
        }
    )

    return mcpServer
}
Part Value Used What it does
name "get_weather" The tool's unique id. The model calls it by this exact name.
description "Get the current weather..." What the model reads to decide whether to call this tool. Write it well.
inputSchema z.object({ city }) Zod schema of arguments the model must send. The model sees this shape.
outputSchema z.object({ temperature, description }) Zod schema of the structured result the tool promises to return.
handler async ({ city }) => {...} The function that actually runs. In real life, this is where you'd hit the weather API.
💡

The handler returns two things: content — plain text for the model to read — and structuredContent — clean JSON matching outputSchema, which the client app can use directly without parsing text.

Step 3 — Mount it on Express
app/app.ts 
import express from 'express';
import type { Request, Response } from 'express';
import { createMcpHandler } from '@modelcontextprotocol/server';
import { toNodeHandler } from '@modelcontextprotocol/node';
import { getMcpServer } from '../mcp/mcp.server.js';

const app = express();

app.use(express.json());

// every MCP request lands on this ONE endpoint
const node = toNodeHandler(createMcpHandler(() => getMcpServer()));
app.all('/mcp', (req, res) => void node(req, res, req.body));

export default app;
Key Concept — One Endpoint

An MCP server doesn't have routes like /tools or /weather. Everything — list the tools, call a tool — arrives on a single endpoint (/mcp). createMcpHandler turns our McpServer into a web handler, and toNodeHandler adapts it to Express's req/res style.

Step 4 — Run it
server.ts 
import app from './app/app.js';

app.listen(3000, () => {
  console.log('Server is running on port 3000');
});
Verify

Run it with npx tsx server.ts. Nothing to see in the browser — an MCP server has no UI. It just sits at http://localhost:3000/mcp waiting for an MCP client to connect. That client is next.

04
Connect the Agent
Any MCP client can use our server — Claude, Cursor, or our own LangChain agent.

Our server is live. Now we play the other role — the AI application. The MultiServerMCPClient connects to one or more MCP servers and hands their tools to our agent as if we had written them ourselves.

mcp-client/agent.ts 
import { createAgent, HumanMessage } from "langchain";
import { ChatMistralAI } from "@langchain/mistralai"
import { MultiServerMCPClient } from "@langchain/mcp-adapters";

// 1. connect to the MCP server
const client = new MultiServerMCPClient({
    mcpServers: {
        weather: {
            url: "http://localhost:3000/mcp",
        }
    },
});

// 2. pull its tools — they arrive as normal LangChain tools
const tools = await client.getTools();

// 3. model + agent — same as always
const model = new ChatMistralAI({
    model: "mistral-small-latest",
    temperature: 0,
    apiKey: process.env.MISTRAL_API_KEY,
});

const agent = createAgent({ model, tools });

const response = await agent.invoke({
    messages: [new HumanMessage("Weather of Bhopal ?")],
})

console.log("Response from agent:", response);
⚠️

Never hardcode API keys in your source files. One git push and the key is public forever. Keep it in an environment variable (process.env.MISTRAL_API_KEY) and put your .env file in .gitignore.

What actually happens when you run this

You ask: "Weather of Bhopal?"
The message goes to the agent.
Model sees get_weather in its tool list
client.getTools() already fetched every tool + description from the server.
Model decides to call get_weather({ city: "Bhopal" })
The description + inputSchema told it how.
MCP client sends the call to http://localhost:3000/mcp
Over the network — the tool code never lived in our agent.
Server runs the handler, returns content + structuredContent
"The current weather in Bhopal is 25°C and sunny."
Model reads the result and writes the final answer
To the agent, an MCP tool is just... a tool. That's the whole point.

05
Transports — STDIO vs Remote
Client and server are separate programs. How do they talk?
Key Concept — Transport

A transport is the channel that carries messages between the MCP client and the MCP server. MCP defines two: STDIO (local) and Streamable HTTP (remote). Same tools, same protocol — only the "wire" changes.

STDIO — the local MCP server

The server is just a program on your own machine. The client (say, Claude Desktop or Cursor) starts it as a child process and they talk through stdin / stdout — the same channels console.log uses. No port, no network, no HTTP.

Remote — the MCP server over Streamable HTTP

The server runs on someone else's machine — Google's, or your company's cloud. It exposes one HTTP endpoint (our /mcp), and clients from anywhere in the world connect over the network. This is what we built with Express — and what Google would build for Calendar.

What STDIO (Local) Remote (Streamable HTTP)
Where it runs Your own machine, as a child process Any server on the internet
How they talk stdin / stdout pipes HTTP requests to one endpoint (/mcp)
Who starts the server The client starts it automatically It's already running, deployed like any web server
How many users One — just you Many — hundreds of companies at once
Auth Usually not needed — it's your machine Needed for real services (OAuth, API keys)
Example A filesystem server reading your local files Google Calendar MCP, GitHub MCP, our Express server
💡

When to use what: tools that need your machine (local files, local DB, personal scripts) → STDIO. Tools serving many users over the internet (a company's API, a product) → Remote. That's why Google's Calendar server must be remote.

06
What MCP Provides — Tools, Resources, Prompts
Tools are just one of three things an MCP server can expose.

We built tools today, but an MCP server can serve three kinds of capabilities. An easy way to remember: Tools do things. Resources know things. Prompts say things.

Capability What it is Who controls it Example
Tools Functions the model can call to take an action The model decides create_event, get_weather
Resources Read-only data attached to the model as context The application decides today's events list, a file, a DB record
Prompts Ready-made prompt templates written by the server author The user decides a "plan-my-week" template (like slash commands)

Resources vs Prompts — when to use what

What Resources Prompts
Gives the model Data to read (content / context) Instructions to follow (a reusable template)
Triggered by The application attaches it automatically The user picks it, like a slash command
Side effects None — strictly read-only None by itself — it only shapes the model's next reply
Use it when The model needs to SEE data before answering ✓ The same well-written prompt is needed again and again ✓
Calendar example calendar://events/today — the raw list of events "Summarize my day and flag conflicts" template
💡

Registering them looks just like tools: registerResource() and registerPrompt() on the same McpServer. If it should change something → Tool. If it should be read → Resource. If it's a reusable instruction → Prompt.
