02
Why anyone bothers
The six things microservices buy you — and the one thing they cost

Before the problem, the promise. Microservices are not an aesthetic choice and they are not "the modern way to write code". They are a trade you make to buy six specific abilities. If you do not need any of these six, you do not need microservices.

1 · Deploy independently

Ship the payment service at 3 PM without touching, testing, or redeploying the other eleven services. Release becomes a Tuesday, not an event.

2 · Scale independently

Image processing needs 20 pods. Login needs 2. In a monolith you pay for 20 copies of everything to get 20 copies of one thing.

3 · Fail independently

The recommendation engine dying should not stop people from checking out. Small blast radius instead of one shared fate.

4 · Choose tech per job

Node for the API, Python for the ML scoring, Go for the high-throughput ingest. Each service picks the right runtime and the right database.

5 · Teams move in parallel

Six teams, six repos, six deploy pipelines, no merge war. Team boundaries and service boundaries line up, so coordination cost drops.

6 · Replace without rewriting

A service is small enough to throw away. Rewriting a 4,000-line service is a sprint. Rewriting a 400,000-line monolith is a startup's death.

⚠️

And the cost, stated up front: you trade code complexity for operational complexity. Function calls become network calls that can time out. One transaction becomes five that can partially fail. One log file becomes twelve. One deploy becomes twelve pipelines. Microservices do not remove complexity — they move it from inside your codebase to between your codebases, where a debugger cannot reach it.

The one-line test

Microservices are an organisational solution before they are a technical one. The core question is not "is my code too big?" — it is "are too many people blocked on the same deploy?" If you are three developers shipping one product, the honest answer is almost always: not yet.

Your login endpoint gets 200 requests/sec and your video-transcoding endpoint gets 5. Both live in one monolith. What does the microservices split actually buy you here?

02
The problem, precisely
A monolith is not bad because it is big. It is bad because everything shares one fate.

Picture the app you have already built in this batch. One Express repo. routes/, controllers/, models/, one .env, one MongoDB, one npm start. It works. It is genuinely the right way to start. So what breaks?

Not the file count. What breaks is that a monolith couples four things that should be independent. Every pain you will ever feel comes from one of these four couplings.

1 · Coupled deployment — one change means one full redeploy
You fixed a typo in the invoice PDF template. To ship it you rebuild, retest and restart the entire application, including checkout, auth and search. Every release is a company-wide risk, so releases get rarer, so each release gets bigger, so each release gets riskier. This loop is why teams end up shipping once a month and dreading it.
2 · Coupled scaling — you can only scale the whole thing
Your image-upload endpoint is CPU-heavy. Your login endpoint is trivial. There is no way to give one more resources without giving the other exactly the same. Horizontal scaling means duplicating 100% of the app — 100% of its memory, 100% of its DB connections — to relieve 5% of it.
3 · Coupled failure — one bad line kills every feature
One unhandled promise rejection, one memory leak in the PDF library, one while loop that never exits — the process dies and it takes login, checkout, search and everything else with it. In Node this is worse than in most runtimes: a single blocking operation stalls the event loop, so every in-flight request across every feature slows down together.
4 · Coupled change — everyone edits the same repo
Twelve developers, one package.json, one test suite, one CI queue. Upgrading a library for one feature forces a compatibility audit across all features. Merge conflicts become a daily tax. Onboarding takes three weeks because there is no "small part" to start with.
Key Concept

The unit of deployment is the unit of failure and the unit of scale. In a monolith all three are the same thing: the whole application. Microservices exist to make that unit smaller. That is the entire idea. Everything else — gateways, brokers, service discovery, tracing — is machinery you add to survive having made that unit smaller.

What a monolith is genuinely good at

Do not walk away thinking monoliths are a beginner mistake. Amazon's Prime Video team famously moved a service back to a monolith and cut cost by ~90%. Shopify, GitHub and Stack Overflow run enormous monoliths. Here is the honest scoreboard:

05
The rules of microservices
Break these and you get a distributed monolith — all the cost, none of the benefit

These are not style preferences. Each rule maps directly to one of the six benefits from section 01. Break a rule and you lose the benefit it was protecting, while still paying the operational bill.

RULE 01
One service = one business capability

Split by what the business does, not by technical layer. order-service, payment-service, notification-service — never controller-service, database-service, validation-service. The test: can you describe the service in one sentence without using the word "and"? If a product manager would recognise the name, the boundary is probably right. In DDD terms this is a bounded context.

RULE 02
Own your data — no shared database

This is the rule people break first and regret longest. If order-service and user-service both read and write the same users collection, then a schema change in one breaks the other, and you can no longer deploy them independently. You have built a distributed monolith. Each service owns its schema; the only way in is through that service's API or events. Need user data inside orders? Store the tiny slice you need (userId, displayName) as a local copy, kept fresh by events.

RULE 03
Independently deployable — the acid test

Can you deploy this service to production, on a Friday, without coordinating with any other team and without deploying anything else? If the answer is no, it is not a microservice yet. This single question catches almost every bad boundary.

RULE 04
Talk only over the network, only through contracts

No shared in-memory state, no shared session object, no reaching into another service's Redis keys. Communication is an explicit, versioned contract: REST or gRPC for request/response, AMQP events for fire-and-forget. The contract is the product; the implementation behind it is nobody else's business.

05
Monolith → microservices: how you decide
Not a vibe. A checklist, a set of prerequisites, and a migration pattern.
Default position

Start with a modular monolith. Always. Martin Fowler calls this "MonolithFirst". You do not know your domain boundaries on day one, and a wrong boundary in a monolith is a refactor, while a wrong boundary in microservices is a migration. Build one app with hard internal module walls — modules/orders/, modules/billing/, each with its own service layer and no cross-imports — and you have earned the right to split later, cheaply, along lines you have actually validated.

Signals that it is time

You do not need all of these. Two or three that genuinely hurt is enough.

Signals that it is absolutely not time

⚠️

Stop if any of these are true: the team is under ~8 engineers; the product is still pivoting and features cross module lines every sprint; you have no CI/CD; you have no centralised logging or metrics; nothing is containerised; or the real problem is slow queries and you are hoping architecture will fix a missing index. Splitting under these conditions produces a distributed monolith — twelve deploy pipelines, twelve log files, and still nobody can ship independently.

Prerequisites — earn these before you split

Automated deploys
One service you cannot deploy with a button becomes twelve services you cannot deploy with a button.
Centralised logs + metrics + tracing
Structured JSON logs shipped somewhere searchable, RED metrics (Rate, Errors, Duration) per endpoint, and correlation IDs. Without these, a distributed bug is unfindable.
Containers + an orchestrator
Docker images and Kubernetes (or ECS). You need scheduling, health checks, rolling deploys and service discovery to exist before you have twelve things to schedule.
A test suite you trust
You are about to change how modules talk to each other. Without tests you will not know what you broke until a user tells you.
Clear ownership
Every service needs a named owner. A service nobody owns is a service nobody patches.

The migration pattern: Strangler Fig

Named after the fig that grows around a host tree until the tree rots away and the fig stands on its own. You never do a big-bang rewrite — every big-bang rewrite you have read about failed. You grow the new system around the old one, one service at a time, with traffic switching gradually.

Step 1 — Put a proxy in front of the monolith
Nothing else changes. All traffic goes client → gateway → monolith. This gateway is the switch you will use for every future move, so install it before you need it.
Step 2 — Modularise inside the monolith first
Move the target capability into its own folder with its own service layer. Delete every cross-module import. If you cannot draw a clean line here, in one codebase with an IDE helping you, you certainly cannot draw it across a network.
Step 3 — Pick the first service to extract
Score candidates on: high pain (deploys or scales badly), low coupling (few dependencies on other modules), clear data ownership, and low business risk. Notifications, media processing, search and reporting are usually the best first cuts. Never start with checkout.
Step 4 — Carve out its data
The hardest step, and the one people skip. Split the tables/collections it owns into its own database. Break foreign keys deliberately, replace joins with API calls or local read-models, and migrate with dual-writes or change-data-capture before you cut over.
Step 5 — Shift traffic gradually at the gateway
Route 1% of /media/* to the new service, then 10%, then 50%, then 100%. Compare error rate and p95 at every stage. The rollback is a routing change, not a redeploy.
Step 6 — Delete the old code, then repeat
If you do not delete it, you now maintain two implementations forever. Deletion is what makes it a migration instead of a duplication. Then choose the next capability and go again.

08
API Gateway vs Load Balancer
They sit next to each other in every diagram and do completely different jobs

This is the single most confused pair in backend interviews. The clean way to hold them apart is to notice that they answer different questions about the same request.

The two questions

A load balancer asks: "I have N identical copies of the same thing — which healthy one gets this request?"

An API gateway asks: "What kind of request is this, is the caller allowed to make it, and which of my many different services should handle it?"

One is about capacity across copies. The other is about policy and destination across capabilities.

The analogy that sticks

A load balancer is the person at the cinema pointing you to whichever of the six identical ticket counters is free. Every counter does the same thing; they only care that the queue is even and that they do not send you to a closed one.

An API gateway is the receptionist in an office building. They check your ID, refuse you if you have already visited fifty times today, log your visit with a badge number, decide whether you need Accounts on floor 3 or Support on floor 7, and translate your request into whatever form that department expects. Different departments, different rules, one front desk.

They are not alternatives — you use both, and usually three times over. A load balancer sits in front of the gateway (because the gateway itself needs multiple replicas), the gateway routes to services, and then something load-balances across each service's pods. In Kubernetes that last one is free: a Service object already load-balances across the pods behind it.

A minimal API gateway you can actually read

Before reaching for Kong or Envoy, write this. Ninety lines of Express, and every gateway responsibility from the table above appears once, in order.

gateway/src/index.js 
import express from "express";
import { createProxyMiddleware } from "http-proxy-middleware";
import rateLimit from "express-rate-limit";
import jwt from "jsonwebtoken";
import { randomUUID } from "crypto";

const app = express();

// ── 1. CORRELATION ID — stamped once, carried everywhere ──────────
app.use((req, res, next) => {
  req.id = req.headers["x-request-id"] || randomUUID();
  res.setHeader("x-request-id", req.id);
  next();
});

// ── 2. RATE LIMIT — abuse stops here, not in twelve services ──────
app.use("/api/auth/login", rateLimit({ windowMs: 60_000, max: 5 }));
app.use("/api",            rateLimit({ windowMs: 60_000, max: 100 }));

// ── 3. AUTH — verified ONCE; services trust the header ────────────
function authenticate(req, res, next) {
  const token = (req.headers.authorization || "").split(" ")[1];
  if (!token) return res.status(401).json({ error: "missing token" });
  try {
    const claims = jwt.verify(token, process.env.JWT_SECRET);
    req.headers["x-user-id"]   = claims.sub;
    req.headers["x-user-role"] = claims.role;
    delete req.headers.authorization;  // never forward the raw token
    next();
  } catch { res.status(401).json({ error: "invalid token" }); }
}

// ── 4. ROUTING TABLE — the heart of the gateway ───────────────────
const routes = [
  { path: "/api/auth",    target: process.env.AUTH_URL,    public: true  },
  { path: "/api/catalog", target: process.env.CATALOG_URL, public: true  },
  { path: "/api/orders",  target: process.env.ORDER_URL,   public: false },
  { path: "/api/media",   target: process.env.MEDIA_URL,   public: false },
];

for (const r of routes) {
  const guards = r.public ? [] : [authenticate];
  app.use(r.path, ...guards, createProxyMiddleware({
    target: r.target,
    changeOrigin: true,
    proxyTimeout: 5000,       // 5. never wait forever on a service
    pathRewrite: { [`^${r.path}`]: "" },
    onProxyReq: (proxyReq, req) => proxyReq.setHeader("x-request-id", req.id),
    onError: (err, req, res) => {     // 6. degrade, never hang
      console.error(JSON.stringify({ lvl: "error", id: req.id, path: r.path, msg: err.message }));
      res.status(503).json({ error: "service unavailable", service: r.path, requestId: req.id });
    },
  }));
}

app.get("/healthz", (_, res) => res.send("ok"));  // 7. for the load balancer
app.listen(8080);
⚠️

Two gateway traps. (1) The gateway is a single point of failure — it must always run multiple replicas behind a load balancer, and it must stay stateless. (2) The gateway is not where business logic goes. The moment you write "if the user's cart total is over ₹5,000 then…" in the gateway, you have started rebuilding the monolith at the front door, and every team now has to coordinate through it again. Smart endpoints, dumb pipes.

So what do we use as the gateway?
CloudFront? Amazon API Gateway? Nginx? The options, the costs, and the decision
⚠️

First, kill the most common confusion: CloudFront is not an API gateway. CloudFront is a CDN. Its job is to cache content at edge locations near the user, terminate TLS early, and absorb traffic before it reaches your region. It has no concept of "verify this JWT against my auth service", no per-API-key rate limits, and no request aggregation. You put CloudFront in front of your gateway. You do not use it instead of one.

The realistic options, side by side

OptionWhat it really isCost shapeVerdict for us
Amazon CloudFront Global CDN. Edge caching, TLS termination, AWS Shield Standard DDoS protection built in, WAF attach point, and VPC origins so it can reach a private ALB without exposing it publicly. Per GB + per request; very cheap for cacheable content Yes — but as the CDN layer, in front
Amazon API Gateway Fully managed API front door. JWT authorizers, throttling, usage plans, request validation. Reaches private EKS services through a VPC Link. HTTP API ≈ $1.00 per million requests (first 300M, us-east-1), REST API ≈ $3.50 per million. Asia-Pacific regions run higher. A VPC Link is billed hourly whether or not traffic flows. Great for serverless / Lambda; expensive and awkward in front of EKS
ALB via AWS Load Balancer Controller A real Layer-7 load balancer that you create from a Kubernetes Ingress or Gateway resource. Path and host routing, TLS from ACM, WAF attachment, OIDC auth. Hourly + LCU; flat and predictable at volume Yes — this is our load balancer

⚠️

Important 2026 update — do not teach or install ingress-nginx. Kubernetes SIG Network and the Security Response Committee announced the retirement of the community ingress-nginx controller, and best-effort maintenance ended in March 2026 — no further releases, bug fixes or security patches. Existing clusters keep routing traffic, but you would be running an unmaintained internet-facing component. Two clarifications students get wrong: the Kubernetes Ingress API itself is not removed (it is still GA, just feature-frozen), and the NGINX web server is completely unaffected. Only that one controller project is retired. Active development has moved to the Gateway API, and the ingress2gateway tool exists to convert existing resources.

Decision for the Codex batch

CloudFront in front · ALB as the load balancer · our own gateway inside the cluster

Learning phase — build the gateway yourself. You cannot understand a gateway you did not write. Ninety lines of Express, and you have personally implemented routing, JWT verification, rate limiting, correlation IDs, timeouts and fallbacks. Every managed product after this is just those same responsibilities with a config file.

Production on our EKS cluster (ap-southeast-1) — four layers, each doing one job:

1. Route 53 api.cryboy.in → CloudFront distribution 2. CloudFront CDN static assets, TLS at edge, AWS Shield, WAF attached ↓ absorbs cacheable traffic your cluster never sees 3. ALB LOAD BALANCER created by AWS Load Balancer Controller ↓ health checks + spreads across gateway pods (X-axis) 4. api-gateway ×3 API GATEWAY our Express service, stateless, HPA-scaled ↓ authN, rate limit, route by path, correlation id (Y-axis) 5. k8s Services LOAD BALANCER (free) ClusterIP spreads across each service's pods ↓ 6. auth · order · catalog · media · payment each with its own database

Why not just put Amazon API Gateway in front of EKS?

You can, and for a Lambda-based product you absolutely should. For a containerised product on EKS, three things push against it. Cost shape: you pay per request forever, and at a few hundred million requests a month that is real money for routing you were already doing in-cluster. Plumbing: reaching private services inside the VPC needs a VPC Link, which is billed hourly even at zero traffic, plus an NLB or ALB behind it anyway. Control: your routing rules live in AWS config instead of in the repo next to the services, so a routing change is a Terraform apply rather than a deploy.

💡

The rule of thumb: if your compute is serverless, use the managed Amazon API Gateway — it is designed for exactly that. If your compute is a Kubernetes cluster, keep the gateway inside the cluster, where it deploys, scales and versions with everything else.

k8s/gateway-ingress.yaml — ALB in front of our gateway 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-gateway
  annotations:
    # provisions a real ALB via the AWS Load Balancer Controller
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/healthcheck-path: /healthz
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:ap-southeast-1:...
spec:
  ingressClassName: alb
  rules:
    - host: api.cryboy.in
      http:
        paths:
          # ALB sends EVERYTHING to the gateway. The gateway does the real routing.
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-gateway
                port: { number: 8080 }

The message broker
You split the monolith. Now the services are wired to each other — and that is its own problem.

Splitting into services solved deployment, scaling and blast radius. It did not solve coupling between services. In fact the naïve version makes it worse, because now the coupling runs over a network that can fail.

The problem: the synchronous chain

Here is the code every team writes first. A customer places an order, so the order service does the obvious thing — it calls everyone who needs to know.

order-service/src/createOrder.js — the version that will hurt you 
async function createOrder(req, res) {
  const order = await Order.create(req.body);            //   30ms

  await axios.post("http://payment-svc/charge",  order); //  400ms
  await axios.post("http://email-svc/confirm",   order); //  600ms  ← 3rd-party SMTP
  await axios.post("http://invoice-svc/generate", order); //  250ms  ← PDF render
  await axios.post("http://analytics/track",     order); //   80ms
  await axios.post("http://warehouse/reserve",   order); //  180ms

  res.json(order);   // customer has been staring at a spinner for 1,540ms
}

Count what is wrong with this — there are five separate failures, and only one of them is speed.

1 · Latency adds up
The customer waits for the sum of every downstream call. Generating a PDF invoice has nothing to do with whether the order was accepted, yet it is on the critical path.
2 · Temporal coupling — all six must be alive at the same instant
Availability multiplies. Six services at 99.9% each gives you 99.4% for the chain — roughly 3.6 hours of downtime a month created purely by wiring things together synchronously.
3 · Failure coupling — the mail server takes down checkout
SMTP is slow this morning, so await email-svc hangs, so the order fails, so you lose the sale. A non-critical service just became critical because of an await.
4 · Change coupling — every new listener edits this file
Fraud team wants order events? Edit and redeploy order-service. Loyalty points? Edit and redeploy order-service. Your "independent" service is now edited by five teams — exactly the monolith problem, wearing a new hat.
5 · Spike coupling — the slowest consumer sets the pace
10,000 orders/minute during a sale means 10,000 PDF renders per minute, whether invoice-svc can do 500 or not. There is no buffer, so the pressure lands directly on the weakest link.
Key Concept

A message broker is a piece of infrastructure that sits between services and holds messages. The producer hands a message to the broker and is done. The broker stores it durably and delivers it to whoever is interested, whenever they are ready.

The producer stops asking "who needs to know about this and are they up right now?" and starts simply announcing "an order was created."

Exactly how a broker decouples: three dimensions

"Loose coupling" is a phrase people repeat without unpacking. Here is the unpacked version — a broker removes three different dependencies, and it is worth being able to name all three.

DimensionDirect HTTP callThrough a broker
Space
(who / where)		 Producer needs the URL, port and API shape of every consumer. Adding a consumer means editing the producer. Producer knows only an exchange name and a routing key. It has no idea who is listening, or whether anyone is.
Time
(when)		 Both must be alive at the same instant. Consumer down = request lost. Consumer can be down for an hour. Messages wait in a durable queue and are processed when it returns.
Synchronisation
(who waits)		 Producer blocks until the consumer answers. Consumer's latency is the producer's latency. Producer publishes in ~2ms and returns. Consumers take as long as they need. Neither one waits for the other.

The rewrite

order-service/src/createOrder.js — the version that survives Black Friday 
async function createOrder(req, res) {
  const order = await Order.create(req.body);              // 30ms

  // Payment stays synchronous — the customer genuinely needs the answer NOW.
  const payment = await paymentClient.charge(order);     // 400ms

  // Everything else: announce it once and move on.
  // order-service does not know email, invoice, analytics or warehouse exist.
  channel.publish("orders", "order.created",
    Buffer.from(JSON.stringify({ ...order, paymentId: payment.id })),
    { persistent: true, messageId: order.id, contentType: "application/json" }
  );                                                     //  2ms

  res.json(order);   // 432ms total, and nothing downstream can break checkout
}
💡

The judgement call is what stays synchronous. Ask: does the user need this answer to continue? Payment authorisation — yes, keep it sync. Confirmation email, invoice PDF, analytics, warehouse reservation, search reindex, loyalty points — no. If the user would never notice it happening 400ms later, it belongs on the queue.

RabbitMQ's model — five nouns you must know

RabbitMQ speaks AMQP 0-9-1, and its one genuinely important idea is this: a producer never publishes to a queue. It publishes to an exchange, and the exchange decides which queues get a copy. That indirection is the decoupling.

Producer ──publish(exchange, routingKey, msg)──▶ EXCHANGE │ bindings match routingKey ──┤ ▼ QUEUE (durable, stores messages) │ ▼ Consumer ──ack──▶ message deleted
NounWhat it isRule of thumb
ConnectionOne TCP connection to the broker.Expensive — open one per process and keep it
ChannelA lightweight virtual connection multiplexed over the TCP connection.Cheap — one per thread/worker. Never share a channel across concurrent consumers
ExchangeThe router. Receives every published message and decides where copies go.Producers only ever know this name
BindingA rule connecting an exchange to a queue, usually with a pattern.Declared by the consumer, which is why adding a consumer needs no producer change
QueueAn ordered buffer that actually stores messages until acked.One queue per consuming service per event type

Step 1 / 7
The precise answer to "how does a broker decouple services?"

Because bindings are declared by the consumer, not the producer. order-svc publishes to the exchange orders with the key order.created and that is the total extent of its knowledge. Every consuming service declares its own queue and binds it to that exchange with whatever pattern it cares about. Adding, removing or breaking a consumer changes nothing on the producer side — no code change, no redeploy, no coordination meeting. The exchange name and routing key are the only contract, and both sides depend on that contract instead of on each other.

RabbitMQ in practice
Reliability settings, the code, and the four mistakes everybody makes
Step 1 — Publish reliably

A default publish() is fire-and-forget: if the broker is restarting, your message silently vanishes. Three settings turn that into a guarantee.

order-service/src/broker/publisher.js 
import amqp from "amqplib";

let channel;

export async function initPublisher() {
  const conn = await amqp.connect(process.env.AMQP_URL);
  conn.on("close", () => setTimeout(initPublisher, 2000));  // always reconnect

  // ConfirmChannel → the broker ACKs us back. Without this you never
  // find out that a publish failed.
  channel = await conn.createConfirmChannel();

  // durable: the exchange definition survives a broker restart
  await channel.assertExchange("orders", "topic", { durable: true });
}

export function publish(routingKey, payload, messageId) {
  return new Promise((resolve, reject) => {
    channel.publish(
      "orders",
      routingKey,                                // e.g. "order.created"
      Buffer.from(JSON.stringify(payload)),
      {
        persistent:  true,                     // write the MESSAGE to disk too
        messageId,                             // consumers dedupe on this
        contentType: "application/json",
        timestamp:   Date.now(),
        headers:     { "x-request-id": payload.corrId, "x-schema": "v1" },
      },
      (err) => (err ? reject(err) : resolve()) // ← publisher confirm
    );
  });
}
💡

durable vs persistent — the classic exam trap. durable: true on a queue or exchange means the definition survives a broker restart. persistent: true on a message means the message content is written to disk. You need both. A persistent message in a non-durable queue dies with the queue; a durable queue full of transient messages comes back empty.

Step 2 — Consume safely
email-service/src/broker/consumer.js 
import amqp from "amqplib";

export async function startConsumer() {
  const conn = await amqp.connect(process.env.AMQP_URL);
  const ch   = await conn.createChannel();

  // ── Dead-letter setup: where poison messages go to be inspected ──
  await ch.assertExchange("orders.dlx", "topic", { durable: true });
  await ch.assertQueue("q.email.dead", { durable: true });
  await ch.bindQueue("q.email.dead", "orders.dlx", "#");

  // ── The work queue. THE CONSUMER declares the binding — this is
  //    the line that makes the producer independent of us.
  await ch.assertQueue("q.email", {
    durable: true,
    arguments: {
      "x-queue-type":              "quorum",      // replicated + HA (RabbitMQ 4.x)
      "x-dead-letter-exchange":    "orders.dlx",
      "x-delivery-limit":          5,             // then dead-letter it
    },
  });
  await ch.bindQueue("q.email", "orders", "order.*");

  // ── PREFETCH: the single most important consumer setting.
  //    Without it RabbitMQ pushes the ENTIRE queue at one consumer
  //    and it runs out of memory while its siblings sit idle.
  await ch.prefetch(10);

  ch.consume("q.email", async (msg) => {
    if (!msg) return;
    const event = JSON.parse(msg.content.toString());

    try {
      // IDEMPOTENCY: delivery is AT-LEAST-ONCE, so this WILL run twice
      // one day. Make the second run a no-op.
      const fresh = await SentLog.create({ _id: msg.properties.messageId })
        .catch(e => (e.code === 11000 ? null : Promise.reject(e)));
      if (fresh) await sendConfirmationEmail(event);

      ch.ack(msg);                     // only now is it deleted from the queue
    } catch (err) {
      const transient = err.code === "ETIMEDOUT" || err.status >= 500;
      // requeue=true  → try again later (SMTP blip)
      // requeue=false → straight to the DLX (malformed message)
      ch.nack(msg, false, transient);
    }
  }, { noAck: false });      // noAck:true = "lose my messages", never use it
}

persistent: trueMessage bodies are written to disk.Every unprocessed message dies with the broker

⚠️

Four mistakes, in the order students make them. (1) Assuming exactly-once delivery. RabbitMQ gives at-least-once. If the network drops between your ack and the broker receiving it, you get the message again. Idempotent consumers are not optional. (2) Forgetting prefetch. Default is unlimited — one worker takes everything. (3) Acking before the work is done. That is at-most-once with extra steps. (4) Using the queue as a database. A queue is a pipe, not storage. If you need to query it, you needed a database.

Ordering, and the honest caveat

A single queue with a single consumer preserves order. The moment you scale to three consumers for throughput, ordering across them is gone — message 3 can finish before message 1. If order matters within an entity (all events for this order), the usual fix is a consistent-hash exchange so all messages with the same key land on the same queue, or you design events so order does not matter (include a version number and ignore stale events). Do not pretend the problem is not there.

Decision for the Codex batch

RabbitMQ — because our problem is routing, not volume

We are decoupling services and running background jobs, not ingesting a billion clickstream events. RabbitMQ's topic exchange, per-message TTL, dead-letter exchanges and simple ops fit that exactly, and it runs in one modest pod on our cluster with a management UI at port 15672 that makes queue depth visible to students during a live demo. Kafka solves a real problem — it is simply not this one.

Recap & checklist
If you remember nine things from these notes, make it these
1 · The unit of deployment is the unit of failure and the unit of scale
Microservices exist to make that unit smaller. Everything else is machinery to survive having done so.
2 · Distributed ≠ microservices
Distributed is a deployment fact (many machines). Microservices is a design choice (split by business capability). Three copies of one monolith is the former, not the latter.
3 · Shared database = distributed monolith
If two services write the same table, they cannot deploy independently, and you have paid the whole bill for none of the benefit.
4 · Modular monolith first, always
Then Strangler Fig. Never a big-bang rewrite. Extract the highest-pain, lowest-coupling capability first — and actually delete the old code.
5 · Try the X-axis before the Y-axis
Adding replicas behind a load balancer is an afternoon. Splitting into services is a quarter. Only split when cloning stops helping.
6 · Load balancer picks a copy; gateway picks a service and enforces policy
You use both. LB in front of the gateway, gateway in front of the services, and Kubernetes Services load-balancing the pods behind each one.
7 · CloudFront is a CDN, not a gateway
Our stack: Route 53 → CloudFront → ALB → our Express gateway ×3 → services. And no new ingress-nginx in 2026 — it is retired.
8 · A broker decouples in space, time and synchronisation
Producers know only an exchange and a routing key. Consumers declare their own bindings. That one inversion is what makes services independent.
9 · Everything on the queue must be idempotent
At-least-once delivery is a promise that you will one day process the same message twice. Design for it on day one, not after the duplicate-invoice incident.

Before you call it a microservice — the checklist

☐ Owns its own database ☐ Deployable alone, on a Friday ☐ Has a named owner ☐ /healthz + /readyz ☐ Structured JSON logs ☐ Propagates x-request-id ☐ Timeout on every outbound call ☐ Retry with backoff + jitter ☐ Circuit breaker on dependencies ☐ Idempotent write endpoints ☐ Containerised + CI pipeline ☐ Versioned, backward-compatible API ☐ Resource requests & limits set ☐ Dashboard: rate, errors, duration
💡

Homework. Take the monolith you already built. Do not split it yet. First draw its capabilities as boxes, mark every place two boxes share a database table, and mark every place one box awaits another. Those two sets of marks are your future service boundaries and your future queue, respectively — and finding them on paper costs a lot less than finding them in production.
